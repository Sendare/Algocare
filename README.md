# Algocare

Exam-prep platform for Nigerian nursing and allied-health students. Static
site + CBT practice app, content generated by Gemini, built via Python,
hosted on GitHub Pages, automated via GitHub Actions. Built and operated
entirely from a mobile phone (Termux + git).

Multi-program: one Algocare instance can serve several exam tracks (basic
nursing, basic midwifery, community health, pharmacy, etc.), each with its
own curriculum, content, and CBT app, under one shared homepage/design.

## Live structure

```
docs/                    <- GitHub Pages root
  index.html              <- program picker (Algocare homepage)
  assets/                 <- copy of shared assets, for the picker page's own CSS
  nursing/                <- one program's full built site
    index.html             <- program homepage (study articles)
    <course-slug>/<unit-slug>/<topic-id>.html
    cbt/                    <- copy of cbt-app/, program-scoped
    data/questions/, data/course_pools/, data/real_feel_tests/
    site_index.json
  midwifery/               <- same shape, once it exists
```

```
                                    own course_id -> course_name grouping

fetch_headings.py  <program>     - Stage 1: headings per topic
fetch_articles.py  <program>     - Stages 2-4: article+questions, engagement rewrite, QA

                                    per-program, all paths are already relative

                                    and once to docs/assets/ for the picker page

.github/workflows/
  fetch_headings.yml    - workflow_dispatch, externally triggered (~10min via cron-job.org)
  fetch_articles.yml    - same trigger pattern
  build_pages.yml       - hourly schedule + manual

```

## Adding a new program

1. Write `curricula/{program}.json` (same schema as `curricula/nursing.json`)
2. Add its course-code mapping to `COURSE_BRANCH_MAPS` in `utils/course_branch_map.py`
3. Copy the 3 workflow files, rename with the program suffix, swap the
   `python fetch_headings.py nursing` argument (and paths in the `git add`
   step) to the new program name
4. Run `fetch_headings.py {program}` until headings are done, then
   `fetch_articles.py {program}` until articles are done, then
   `build_pages.py {program}`
5. Add an entry to `docs/index.html`'s program picker (one `topic-card` block)

No changes needed to `utils/`, `cbt-app/`, or `assets/` - they're already
program-agnostic.

## ID conventions

- `course_id`: official course code (e.g. `GNS111`)
- `topic_id`: `{course_id}_U{unit_number}_T{topic_index}` e.g. `GNS111_U1_T1`
- `heading_id`: `{topic_id}_h{order}` - regenerated fresh at article-generation
  time, since the article stage can revise headings vs. the original proposal
- `question_id`: `{topic_id}_h{order}_q{i}`

## Generation pipeline (per topic, fully resumable)

Each topic completes and saves before moving to the next - any run can be
cut off anytime with zero lost progress.

1. **`fetch_headings.py`** - 1 Gemini call/topic. 5-10 headings, explicitly
   NOT forced into a fixed template - varies structure per topic.

2. **`fetch_articles.py`** - 3 Gemini calls/topic:
   - **Article + questions**: may revise the proposed headings. Content
     uses limited markdown (bold, lists, tables - converted to real HTML
     by `build_pages.py`'s `markdown_to_html()`). Questions: options
     returned as an **unlabeled array**, answer as **exact matching text**,
     never a letter - the script verifies the match
     (`finalize_options()`), discards on mismatch, shuffles, and assigns
     A-D itself. This exists because a model asked to independently
     produce a lettered options dict AND a matching answer letter can
     internally mismatch the two - text-match verification catches that,
     and also guarantees even letter distribution (unprompted, models
     cluster ~80% on one letter).
   - **Engagement/approachability rewrite pass**: separate call per topic,
     reviews every question for tone/simplicity/daily-usability, may
     rewrite (same verification applied to any rewrite).
   - **QA correctness pass**: separate call, pass/fail per question.
     Schema asks for `reasoning` BEFORE `pass`/`fail` - critical detail,
     since a verdict-first schema lets the model commit before it's
     actually reasoned, with no way to revise a wrong first instinct.
     Failing questions are dropped, never "fixed" blind.
   - Learn-more links (`[learn more](topic_id#heading_id)`) are stripped
     before any rewrite and deterministically reattached after, from the
     question's own stored IDs - never trusted to survive a rewrite intact.

3. **`build_pages.py`** - no AI calls. Renders HTML, builds nav, per-course
   question pools, and real-feel exams (weighted sampling + a final
   `random.shuffle()` to eliminate presentation-order clustering).
   Self-cleaning: if `real_feel_state.json` shows `tests_built: 0`, wipes
   any stale leftover exam files itself before rebuilding.

## CBT app (`cbt-app/`)

- **`practice.js`**: topic/course-based practice, `sessionStorage`
  persistence. Timer uses an absolute end-timestamp recalculated on every
  render, not a decrementing counter - immune to throttled/backgrounded
  mobile tabs. Pause tracked via one reconciled timestamp
  (`reconcilePause()`), not per-tick increments.
- **`real_feel.js`**: fixed-size timed exam, same timer pattern, no pause.
- Both: results show attempted/total, correct, score-of-attempted %,
  score-of-total % as 4 lines. Star-rating + comment widget on completion.
- **`analytics.js`**: anonymous `localStorage` UUID, logs
  started/finished/abandoned events + reviews to Supabase via
  `fetch(..., {keepalive:true})` (not `sendBeacon` - can't set auth
  headers). Insert-only via Supabase Row Level Security.

## Known gotchas

- Avoid the `google-genai` SDK - `pydantic-core` has no prebuilt wheel on
  some environments (e.g. Termux/Python 3.14). `utils/ai_client.py` uses
  raw REST via `urllib`, stdlib only.
- `GEMINI_API_KEYS` is one comma-separated secret (not N separate ones),
  rotated only on quota/429 errors.
- `json.loads(raw, strict=False)` + one automatic retry recovers most
  transient malformed-JSON responses cheaply.
- A local sparse git checkout may not include `docs/` at all - any
  cleanup logic that MUST happen belongs inside scripts that run on
  GitHub Actions' full checkout, never assumed to work from a local
  `rm -rf`.
- A difficulty instruction controls cognitive complexity, not language
  complexity - needs a separate explicit plain-language directive.
- JSON schema field order affects LLM self-consistency: reasoning fields
  before verdict fields, always, in any schema asking a model to judge
  something.

- **Found and fixed a real re-render bug while shipping the footer**:
  `build_pages.py` only renders an article/topic page once - a topic
  already in `published_done` never gets its HTML regenerated again,
  even if the shared template changes. Since midwifery's articles were
  already 100% published, the footer would have silently never reached
  a single existing topic page. Added a `--force` flag that re-renders
  every article page regardless of publish state - safe and free since
  page rendering is pure local templating from already-downloaded JSON,
  no AI calls involved. Verified it doesn't create duplicate
  `published_done` entries before relying on it.
- **Real-feel exam course scoping**: NMCN's professional exam doesn't
  test every course in the curriculum (general first-year sciences like
  Physics/Chemistry/English, plus practicum/seminar/capstone courses,
  aren't part of the licensing exam). Two things had to be solved:
  - **Mechanism**: found that using `weight: 0.0` to exclude a course
    from `weighted_sampling.py`'s pool would silently pile up
    never-selected questions forever, risking an eventual crash
    (`random.choices()` on an all-zero-weight remainder). Fixed by
    adding a dedicated `excluded_from_real_feel` list in `weights.json`,
    filtered out of the pool entirely *before* weighting - the excluded
    course's study articles and regular practice pool are untouched,
    it just never appears in the simulated professional exam.
  - **Scope**: 8 branches excluded from real-feel only (Applied Physics,
    Applied Chemistry, Use of English, Behavioral Science,
    Hospital-Based Clinical Practice, Seminar in Midwifery Practice,
    Research Project, Expectant Family Care Project), 18 branches
    included.
- **Weighting**: built a 5-tier target scale (2.5 down to 0.6) reflecting
  likely NMCN exam emphasis - core midwifery-specific clinical content
  (Midwifery Practice, Complicated Midwifery, Reproductive Health, Child
  Health, Infant Care, Family Planning) and requested emphasis courses
  (Primary Health Care, Community Midwifery) weighted highest, general
  supporting sciences in the middle, administrative/soft-skill courses
  (Informatics, Research and Statistics, Management and Teaching)
  weighted lowest.
- **Wrote `check_weight_balance.py` from scratch** - it didn't exist in
  the repo despite being referenced in `weights.json`'s own readme note.
  Reads real per-course question counts from `data/{program}/questions/`,
  divides each target weight by its course's actual count, and writes
  the volume-corrected weights back - so appearance % matches intended
  target regardless of how much content got generated per course. Ran
  it for real: all 18 included branches came back with target % exactly
  matching realized %, no thin-content warnings.
  - **Operational finding worth remembering**: volume correction only
    balances the *per-draw* probability while a course's question supply
    lasts. A course's total lifetime contribution across all real-feel
    tests combined is hard-capped by its actual question count - no
    weight can manufacture content that doesn't exist. Confirmed via a
    live test: a 10-question course dropped to 0% representation in
    later tests once its supply was exhausted, despite equal weighting
    with a 100-question course. If a branch is consistently
    under-represented long-term, the fix is generating more content for
    it, not raising its weight further.
